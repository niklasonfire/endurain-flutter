# Android update publishing

`Build Android` is the shared allocator and publisher for the fork. It runs
only in `niklasonfire/endurain-flutter`, serializes both channels, and preserves
`com.endurain.endurain.local` and the existing certificate documented in
[BUILDING_LOCAL.md](../BUILDING_LOCAL.md). The certificate secret must match
`3341bbf406214b746b6f893d12a353652df6c9215feb6b2e58e541c2bb9dfb6e`.
No new key is generated.

## Triggering a build

After integration into `main`, successful `Local runner CI` push runs produce
Nightly automatically. The publisher checks the exact commit and that formatting,
analysis, coverage, Android unit tests, and the debug build actually ran and
succeeded. Documentation-only and stale automatic candidates skip signing and
building. A pull request CI run or manual smoke check cannot authorize publishing.

To release Stable, run `Build Android` **from main**, select `stable`, supply
`version_name` as `X.Y.Z`, and supply the full 40-character `source_commit` SHA.
That SHA must already have passed complete main-push CI. Stable can use an older
validated commit; Nightly must still be the current main commit at publication.
`check` instead keeps the verified APK and manifest as Actions artifacts without
publishing. `signing_check_only` verifies credentials without building an APK;
it still requires the same trusted source gate.

Manual workflow execution and release publication are remote actions and require
explicit user authorization when performed by an agent.

## Version and asset contract

The Android code is `100000 + github.run_number` from this one workflow, for
both channels. The gate checks every existing release, including drafts, before
allocation and again before publishing. The known previously distributed local
code is 21. Before first publication, audit any APKs distributed outside this
repository against this initial floor. Do not independently distribute local
builds with competing codes. Renaming/replacing the workflow or exhausting the
Android maximum of 2100000000 requires an explicit numbering migration.

Stable is `vX.Y.Z+CODE`, published only after a draft contains its APK and
`update.json`. Nightly is a rolling public prerelease at `nightly`, never Latest;
its tag moves to the verified source commit. Nightly version names use the source
pubspec version followed by `-nightly.CODE`. Changes are generated by GitHub,
relative to the previous release in that channel when available.

Metadata is created from `aapt` and `apksigner` output for the actual APK, checking
package, version, ABI and the pinned certificate. Asset length and SHA-256 come
from the APK bytes. The initial ABI is `arm64-v8a`. APK names are unique:
`endurain-local-CODE-arm64-v8a.apk`. The schema is documented in
[in-app-update-channels.md](in-app-update-channels.md#kanäle-und-release-vertrag).

Nightly uploads the APK first and replaces `update.json` last. Previous APKs stay
available for clients that already read their manifest. A brief missing-manifest
window is possible and the app asks the user to check again. Retention cleanup
must preserve APKs still referenced by manifests or active downloads.

## Failures and recovery

Rerunning the same workflow run is deliberately rejected: start a new run for a
new code. A failed build never updates the channel. A failed Stable upload may
leave a draft; after inspecting the failure, delete that incomplete draft before
starting a fresh run if it contains an APK without metadata. Existing APK
releases without `update.json` block allocation until their actual version codes
are audited; do not guess their ordering. Draft assets are read with repository
authentication and credentials are removed from asset redirects.

Do not overwrite an existing Stable release. Nightly can briefly be unavailable
if pointer replacement fails; inspect the uploaded APK and publish a fresh run
rather than rebuilding under the same code. Keystore and temporary publisher
files are removed in an always-run cleanup step.

The workflow is implemented locally; merging it activates automatic Nightly.
No workflow execution, secret changes or release publication is needed to review
this implementation. The first APK containing the updater must be installed by
the existing distribution route once. Device installation and cross-channel
upgrade validation remain necessary before distributing that bootstrap APK.
